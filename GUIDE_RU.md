# Как понять и показать вариант 15 с нуля

## 1. Что вообще требуется

Нужно написать маленькую программу, которая выясняет, какие готовые
компоненты нужны друг другу, и рисует их связи.

Представь конструктор. Чтобы собрать дом A, нужны наборы B и C.
Для набора B нужен D. Для C нужны D и E.
Наша программа не строит дом: она составляет список и схему,
что от чего зависит.

В настоящем задании вместо наборов — программные пакеты NuGet.
Пакет — готовый кусок программы. NuGet — каталог таких пакетов
для платформы .NET. .NET — платформа для запуска и разработки программ,
например на C#. Сам анализатор написан на Python: это разрешено методичкой.

Вариант 15 находится на страницах 50–52 PDF. Не путай с эмулятором терминала
в соседней папке: это другое задание.

## Запуск в терминале VS Code

Открой папку NuGet_Variant_15 в VS Code: «Файл → Открыть папку».
Выбери «Терминал → Создать терминал» и выполни команды по очереди:

```powershell
python -m pip install -r requirements.txt
python main.py --test --repository data/branch.json --package A --version 1.0.0
Invoke-Item .\output\graph.png
```

Если открыта родительская папка, сначала введи `cd .\NuGet_Variant_15`.
Если python не найден, на этом компьютере подключи имеющийся Python для текущего
терминала следующей командой, затем повтори запуск:

```powershell
$env:Path = "$env:USERPROFILE\.cache\codex-runtimes\codex-primary-runtime\dependencies\python;$env:Path"
```

На другом компьютере нужен Python 3.10+ с добавлением в PATH.
Программа сохраняет PNG, команда Invoke-Item открывает его в просмотрщике Windows.
Для рисования используется установленный Graphviz, а если его нет — Pillow.

Проверки: `python -m unittest discover -s tests -v`.

## 3. Словарь без сложных слов

| Слово | Простой смысл |
|---|---|
| Пакет | Готовый компонент программы |
| Зависимость | Компонент, без которого другому компоненту не обойтись |
| Репозиторий NuGet | Источник, где лежат пакеты и их описания |
| Версия | Конкретный выпуск пакета, например 1.0.0 |
| Граф | Точки и стрелки между ними |
| Вершина | Один пакет с определенной версией |
| Ребро | Стрелка зависимости |
| Прямая зависимость | A сразу использует B |
| Транзитивная зависимость | A использует B, а B использует D; D косвенно нужен A |
| Обратная зависимость D | Ответ на вопрос: кому нужен D? |
| CLI | Программа, которой задают настройки текстовой командой |
| JSON | Текстовый формат хранения данных, похожий на списки и карточки |
| XML / nuspec | Текстовое описание настоящего пакета NuGet |
| DFS | Обход: идем по одной ветке в глубину, затем возвращаемся к оставшимся |
| Стек | Стопка задач: последнюю положили — первой взяли |
| Рекурсия | Функция вызывает сама себя; в этом задании для DFS запрещена |
| Graphviz DOT | Язык: текстом перечисляются точки и стрелки схемы |
| Git | История изменений файлов проекта |
| Коммит | Сохраненный шаг в этой истории |
| README | Инструкция, которая открывается на странице репозитория |

NuGet-репозиторий и Git-репозиторий — разные вещи.
Первый хранит пакеты; второй — исходный код твоей работы и его историю.

## 4. Как вводить команды

В VS Code открой «Терминал → Создать терминал» в папке NuGet_Variant_15.

Вставляй команды ниже целиком. После каждой нажимай Enter.
`--` означает название настройки. Слова после него — ее значение.
Например `--package A`: анализировать пакет A.
`python` запускает Python; `main.py` — наша программа.

## 5. Показать первый этап — настройки

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --max-depth 3 --stage 1
```

Появятся строки package=A, version=1.0.0 и другие настройки.
Это ожидаемый результат: первый этап проверяет настройки, а не строит граф.

Скажи: «Параметры передаются через командную строку. Я задаю имя пакета,
версию, источник данных, тестовый режим, глубину и фильтр. На первом этапе
программа выводит эти параметры, чтобы проверить настройку».

Показать неправильную глубину:

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --max-depth -1 --stage 1
```

Должна появиться понятная ошибка.
Это правильно: отрицательного числа уровней быть не может.
Другие проверки запускаются командой `python -m unittest discover -s tests -v`: неверное имя, версия, URL, файл, фильтр.

## 6. Второй этап — прямые зависимости

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --stage 2
```

Ожидаемый результат: B и C с диапазоном [1.0.0].
Квадратные скобки вокруг одной версии означают «нужна точно эта версия».
D и E пока не выводятся: они нужны не самому A напрямую.

Скажи: «На этом этапе извлекаются только прямые зависимости. В реальном
режиме описание скачивается из NuGet по HTTP, затем программа сама разбирает XML».

## 7. Третий этап — вся цепочка

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --stage 3 --max-depth 3
```

Будут связи A с B и C, B с D, C с D и E.
F не будет: от A до F нет пути.
`@1.0.0` после имени — версия пакета, а не часть имени.

Теперь поменяй только `--max-depth 3` на `--max-depth 1`.
Останутся A, B, C. Пакеты D и E дальше разрешенной глубины.
B и C при этом будут без раскрытых связей: программа остановилась на границе,
это НЕ доказательство отсутствия у них собственных зависимостей.

Исключить B:

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --stage 3 --max-depth 3 --filter B
```

B исчезнет, но D останется: к нему можно прийти через C.
Если путь к пакету был только через исключенную вершину, он тоже исчез бы.

Показать цикл:

```powershell
python main.py --test --repository data/cycle.json --package A --version 1.0.0 --stage 3 --max-depth 100
```

Получится A нужен B, B нужен C, C нужны A и D. Программа завершится.
Она запоминает уже рассмотренные вершины и не ходит бесконечно по кругу.

Скажи: «Использован DFS без рекурсии. Непросмотренные вершины лежат в стеке.
Программа достает вершину, добавляет ее зависимости и продолжает обход.
Для вершины запоминается наименьшая глубина посещения: так обрабатываются
циклы и короткие пути к ранее найденной вершине».

## 8. Четвертый этап — кому нужен пакет D

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --stage 4 --reverse D --max-depth 3
```

Ожидаемый результат: A, B, C, F.
B, C, F используют D напрямую; A — через B и C.
F появляется потому, что обратный поиск в тестовом режиме смотрит
весь файл репозитория, а не только ветку от A.
Если поставить глубину 1, останутся только B, C, F.

Скажи: «Переворачиваю стрелки графа и снова выполняю обход стеком.
Так нахожу пакеты, зависящие от выбранного пакета».

В реальном NuGet программа знает только уже исследованную часть графа,
поэтому обратные зависимости там ограничены этой частью.
Она не скачивает описание каждого пакета во всем NuGet.

## 9. Пятый этап — схема

Команда ниже создаст output/graph.png. Открой картинку командой
`Invoke-Item .\output\graph.png`.
Белый фон, блоки со скругленными углами, стрелки слева направо.

Ручной запуск из PowerShell в папке проекта:

```powershell
python main.py --test --repository data/branch.json --package A --version 1.0.0 --stage 5 --png output/graph.png
```

После ручного запуска открой output/graph.png двойным щелчком.
Готовые examples/A.png, B.png, C.png показывают три разных пакета.
Текст схемы Graphviz выводится в консоль и сохраняется в output/graph.dot.
Если установлен Graphviz, картинка рисуется его движком.
Иначе для рисования используется Pillow. В текущем Python она уже есть.
Если на другом компьютере появится сообщение, что Pillow отсутствует:

```powershell
python -m pip install -r requirements.txt
```

Скажи: «Программа формирует описание графа на языке Graphviz DOT,
выводит его на экран и сохраняет в файл. Дополнительно сохраняется
картинка PNG, которую можно открыть в обычном просмотрщике».

```powershell

python main.py --package Humanizer.Core --version 2.14.1 --max-depth 2 --output output/Humanizer.dot --png output/Humanizer.png
python main.py --package Microsoft.Extensions.Logging --version 8.0.0 --max-depth 2 --output output/Logging.dot --png output/Logging.png
```


Проверку настоящего API из текущей среды заблокировал Windows: ошибка 10013.
Это не успешный сетевой тест. До окончательной сдачи нужно прогнать примеры
из обычного терминала с доступом в интернет и выполнить сравнение из README.
Не говори преподавателю, что это уже проверено, пока не увидишь результат.

Если спросят, почему схема отличается от Visual Studio:
«По умолчанию объединяются зависимости всех групп .NET из nuspec.
Visual Studio выбирает группу под конкретную платформу проекта.
Еще здесь нет полноценного разрешения конфликтов версий всего проекта».
Это объяснение возможных причин, а не замена фактического сравнения.

## 11. Частые вопросы преподавателя

**Что разработано?**
Инструмент построения графа зависимостей пакетов NuGet.

**Откуда данные?**
Из описания .nuspec в NuGet, а для учебной проверки — из JSON-файла.

**Почему Python, если пакеты .NET?**
Python только анализирует описания пакетов. Методичка разрешает выбирать язык.

**Использовались ли готовые библиотеки зависимостей?**
Нет. HTTP, JSON и XML обрабатываются стандартными средствами Python,
обход графа написан самостоятельно.

**Как учитывается версия?**
Для корня задается точная версия. Для зависимости из ее диапазона
выбирается минимальная подходящая версия. Вершина включает имя и версию.

**Что означает глубина 0?**
Только корневой пакет; его зависимости не загружаются.

**Почему DFS не рекурсивный?**
Так требуется в варианте 15. Вместо вызовов функции используется стек.

**Как исключаются циклы?**
Повторное посещение на той же или большей глубине пропускается.
Сама стрелка цикла при этом сохраняется.

**Почему используете наименьшую глубину?**
К одному пакету могут вести длинный и короткий пути. После короткого пути
остается больше разрешенных уровней, поэтому зависимости надо раскрыть снова.

**Фильтр только прячет подписи?**
Нет. Пакеты с этой подстрокой исключаются из анализа вместе с их ветками.

**Почему D после исключения B остался?**
Его использует еще и C, который не исключен.

**Какой алгоритм обратного поиска?**
Разворот ребер и DFS со стеком.

**Что проверяют тесты?**
Глубину, фильтр, циклы, повторный короткий путь, обратные связи,
пустой граф, диапазоны версий, XML и неправильные параметры.

**Где история этапов?**
В локальном Git: команда git log --oneline. Для сдачи нужен публичный
репозиторий; публикация еще предстоит.

## 12. Речь на 40–60 секунд

«У меня вариант 15: визуализация зависимостей NuGet.
Программа получает имя и версию пакета, источник данных, глубину и фильтр
через командную строку. Она читает описание пакета и самостоятельно
извлекает зависимости. Граф строится обходом в глубину без рекурсии,
для обхода используется стек. Учтены циклы, ограничение глубины и
исключение пакетов по подстроке. Отдельно реализован поиск обратных
зависимостей. Результат выводится на языке Graphviz DOT.
Для проверки без интернета есть небольшие репозитории с ветвлением,
циклом и пакетом без зависимостей. Эти случаи проверяются тестами».

## 13. Что осталось до окончательной сдачи

1. Самому пройти команды выше: увидеть результаты и понять стрелки.
2. Запустить три реальных пакета при доступном интернете.
3. Выполнить независимое сравнение со штатным инструментом — инструкции в README.
4. Опубликовать Git-репозиторий и передать преподавателю его ссылку.
5. Быть готовым открыть graph.py и показать стек и проверку глубины.

Одной заученной речи недостаточно, если преподаватель попросит поменять
глубину или объяснить конкретную стрелку. Но для этого не нужно учить
весь Python: достаточно самостоятельно пройти демонстрации из этого файла.
